ปัญหาที่พบในกระบวนการปัจจุบัน (Problem Statement)

การจัดคิวแบบกระดาษ

เจ้าหน้าที่ต้องจดบันทึกด้วยมือ เสี่ยงต่อการเรียกคิวผิดลำดับ และผู้โดยสารต้องยืนรอที่ท่ารถโดยไม่ทราบลำดับที่ชัดเจน

ความล่าช้าและการเสียโอกาส

หากผู้โดยสารไม่อยู่ในจุดรอจะถูกข้ามคิว ทำให้ผู้โดยสารเสียเวลา และคนขับจัดการที่นั่งว่าง (No-show) ได้ลำบาก

ขาดความโปร่งใสและข้อมูล

ผู้โดยสารไม่สามารถติดตามตำแหน่งรถตู้ ไม่มีการแจ้งเตือนแบบเรียลไทม์ และผู้ให้บริการไม่มีข้อมูลสถิติเพื่อพัฒนาบริการ

วัตถุประสงค์ของโครงงาน (Objectives)

  • พัฒนาระบบฝั่งผู้โดยสาร (Passenger Web App) เพื่อให้ผู้โดยสารจองคิวรถตู้ล่วงหน้า ตรวจสอบลำดับคิว และติดตามตำแหน่งรถตู้ได้อย่างสะดวกด้วยตนเอง
  • พัฒนาระบบฝั่งคนขับ (Driver Dashboard) สร้างหน้าจอสำหรับคนขับในการดูรายชื่อผู้โดยสาร จัดการคิว ตรวจสอบสลิปโอนเงิน และยืนยันสถานะการออกรถ
  • จัดเก็บข้อมูลในฐานข้อมูลส่วนกลาง จัดเก็บข้อมูลผู้โดยสาร รถตู้ เส้นทาง และรอบการเดินรถ เพื่อรองรับการนำไปวิเคราะห์สถิติในอนาคต
  • ทดสอบประสิทธิภาพ (Usability Testing) ประเมินการใช้งานของระบบต้นแบบ ทั้งด้านการทำงานของฟังก์ชัน (Functional) และประสบการณ์ผู้ใช้ (UX)

ขอบเขตของโครงงาน (Scope of Work)

สิ่งที่ระบบรองรับ (In-Scope)

  • รองรับเส้นทางหลักจาก ม.ธรรมศาสตร์: จตุจักร, อนุสาวรีย์ชัยฯ, ฟิวเจอร์พาร์ค รังสิต
  • ใช้งานผ่าน Web Application บนอุปกรณ์พกพา
  • ระบบการแจ้งเตือนแบบเรียลไทม์ (Push Notification)
  • ระบบจำลองการเลื่อนคิวและยกเลิกตั๋วอัตโนมัติ (Cutoff time)
  • ระบบจัดการสลิปการโอนเงิน (ตรวจสอบโดยคนขับ)

สิ่งที่อยู่นอกเหนือขอบเขต (Out-of-Scope)

  • ไม่รองรับเส้นทางอื่นนอกจากที่กำหนดไว้ในระบบต้นแบบ
  • ยังไม่เชื่อมต่อกับระบบ Payment Gateway อัตโนมัติ (ปัจจุบันใช้การอัปโหลดสลิปเพื่อให้คนขับตรวจสอบ)
  • ความแม่นยำของ GPS ขึ้นอยู่กับอุปกรณ์ของคนขับและสัญญาณอินเทอร์เน็ต

บริบทการใช้งาน รถตู้ระยะสั้น / พื้นที่จำกัด (มธ.) รถทัวร์ระยะไกลเชิงพาณิชย์ แอปรวบรวมสายรถตู้ทั่วไป
การจัดคิวแบบ Real-time (FCFS) มีระบบรันคิวออนไลน์และ Walk-in จองตั๋วตายตัว ไม่มีรันคิว ไม่มีระบบจอง
ระบบจัดการที่นั่ง (Run-up Queue) ตัดสิทธิ์คนไม่มา เติมที่นั่งอัตโนมัติ ไม่มี ไม่มี
ระบบฝั่งคนขับ (Driver UI) เช็กอิน, ตรวจสลิป, แจ้งรถออก เน้นลูกค้าเป็นหลัก ไม่มี

สรุป: ระบบเดิมไม่ตอบโจทย์การจัดการคิวที่มีความหนาแน่นสูงในช่วงเวลาเร่งด่วนหน้าท่ารถ

แนวคิดของระบบที่นำเสนอ (Proposed Solution)

1. นโยบายโควตาที่นั่ง (50/50 Quota)

เพื่อความยุติธรรม ระบบแบ่งที่นั่งรถตู้ (N ที่นั่ง) เป็น 2 ส่วน:

  • 50% สำหรับจองออนไลน์ (Online) จูงใจให้วางแผนล่วงหน้า ลดความแออัดหน้าท่า
  • 50% สำหรับ Walk-in รองรับผู้โดยสารที่มาถึงหน้าท่าโดยตรง

2. การแบ่งประเภทผู้โดยสาร (Priority Tiers)

  • Online + Paid: จ่ายเงินแล้ว การันตีที่นั่ง (มาสายได้ 5 นาทีหลังรถออก)
  • Online + Unpaid: จองแต่ยังไม่จ่าย (คิวรอ) ต้องมายืนยันและจ่ายเงินก่อนรถออก 15 นาที
  • Walk-in + Paid: มาหน้าท่า จ่ายเงิน ได้คิวตามลำดับเวลาที่มาถึง

3. Time-based Cutoff

มีระบบ Run-up Queue อัตโนมัติ หาก Online+Unpaid ไม่มาแสดงตัวตามเวลา Cutoff ระบบจะตัดสิทธิ์และนำที่นั่งไปเติมให้กลุ่ม Walk-in เพื่อให้รถออกตรงเวลา

ขั้นตอนการทำงานหลัก (Workflow Design)

1. Check & Book

ผู้โดยสารเช็กคิวว่าง เลือกรอบรถ และเลือกประเภทจอง (ชำระทันที/จ่ายหน้าท่า)

2. Verify Slip

ผู้โดยสารอัปโหลดสลิปเข้าสู่ระบบ คนขับตรวจสอบความถูกต้องผ่านหน้า Dashboard

3. Cutoff & Run-up

ระบบตัดสิทธิ์คนไม่จ่ายเงินตามเวลา (15 นาทีก่อนออก) และเติมที่นั่งให้ Walk-in อัตโนมัติ

4. Depart & Notify

คนขับกด "รถใกล้ออก" ระบบส่ง Push Notification แจ้งเตือน และกดยืนยันเมื่อถึงปลายทาง

สรุปปัญหาที่พบจากผู้ใช้ (Results & Discussion)

ปุ่มอัปโหลดสลิปมองเห็นยาก

ปัญหา: ผู้ใช้หลายคนต้องใช้เวลาหาปุ่มอัปโหลดสลิป
แนวทางแก้ไข: ปรับปรุง UI เพิ่มคอนทราสต์ของปุ่ม และจัดวางให้อยู่ในจุดที่มองเห็นได้ชัดเจนทันที

ความสับสนเรื่องคำศัพท์

ปัญหา: ผู้ใช้ไม่เข้าใจคำว่า "Run-up Queue" และประเภทคิว (Paid/Unpaid)
แนวทางแก้ไข: เพิ่มคำอธิบาย (Tooltip) และปรับใช้ภาษาไทยที่เข้าใจง่ายขึ้น

ความหน่วงของระบบ

ปัญหา: ขั้นตอนอัปโหลดไฟล์สลิปใช้เวลาโหลดนาน
แนวทางแก้ไข: จำเป็นต้องทำ Image Compression ก่อนอัปโหลด และปรับปรุง Caching ในอนาคต

สรุปผลการดำเนินงาน (Conclusion)

ระบบเปลี่ยนกระดาษสู่ดิจิทัลได้สำเร็จ

โครงงานนี้บรรลุเป้าหมายในการพัฒนาระบบต้นแบบที่ช่วยเปลี่ยนการเข้าคิวกระดาษหน้าท่ารถ ให้กลายเป็นระบบออนไลน์ที่โปร่งใส

ระบบ Time-based Cutoff และ 50/50 Quota ช่วยรักษาความเป็นธรรมระหว่างผู้โดยสารจองล่วงหน้าและ Walk-in พร้อมลดภาระงานของคนขับได้อย่างเป็นรูปธรรม

ข้อจำกัดของระบบ (Limitations)

  • ความเสถียรของอินเทอร์เน็ต หากสัญญาณไม่ดีหรือ Server ล่ม ระบบจะหยุดชะงัก (Downtime Risk) จำเป็นต้องมีแผนสำรองแบบ Manual เพื่อใช้หน้าท่ารถ
  • การตรวจสลิปเป็นแบบ Manual เวอร์ชันต้นแบบยังใช้คนขับตรวจสอบสลิปด้วยสายตา ซึ่งอาจล่าช้าและเกิด Human Error ในช่วงที่มีผู้โดยสารจำนวนมาก
  • ความซับซ้อนของนโยบาย Cutoff การแบ่งประเภท Walk-in, Paid, Unpaid ทำให้กฎการตัดสิทธิ์มีความซับซ้อน ต้องอาศัยการสื่อสารให้ผู้ใช้เข้าใจอย่างชัดเจน
  • ข้อจำกัดของระบบ GPS ระบบติดตามตำแหน่งยังพิงพิกัดจากอุปกรณ์ของคนขับเพียงอย่างเดียว อาจไม่แม่นยำหากถูกปิดแอปหรือสัญญาณ GPS ขาดหาย
